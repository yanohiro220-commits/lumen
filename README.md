# lumen

A programming language implemented from scratch in C++20: lexer, Pratt parser,
AST optimizer, bytecode compiler with a peephole pass, a stack VM with
computed-goto dispatch, and a precise mark-and-sweep garbage collector.

No third-party dependencies — including the test framework.

```
git clone https://github.com/yanohiro220-commits/lumen
cd lumen && cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j

./build/lumen examples/sorting.lum
./build/lumen --dump examples/fizzbuzz.lum    # print the generated bytecode
./build/lumen --stats examples/primes.lum     # optimizer and VM counters
./build/lumen                                 # REPL
```

```
# lumen
fn counter() {
  let n = 0;
  return fn() { n = n + 1; return n; };     # closures capture by reference
}
let next = counter();
print next(); print next();                  # 1, 2

fn map(xs, f) {
  let out = [];
  for (let i = 0; i < len(xs); i = i + 1) { push(out, f(xs[i])); }
  return out;
}
print map([1, 2, 3], fn(x) { return x * x; });   # [1, 4, 9]
```

## The pipeline

```
source ──► lexer ──► parser ──► optimizer ──► compiler ──► VM
           tokens    AST        AST'          bytecode     values
                                                │
                                          peephole pass
```

Five separable stages, each testable on its own. That is the reason for the
shape: a single-pass compiler that goes straight from tokens to bytecode is
shorter and cannot do the interesting rewrites, because by the time a dead
branch is a run of instructions with jumps into it, deleting it safely is much
harder than never emitting it.

### Values

A value is 8 bytes, NaN-boxed. An IEEE-754 double has 2^52 quiet-NaN bit
patterns that no arithmetic produces, so everything that is not a number is
encoded as one of them. No tag byte, no padding to 16 bytes, and the common
case — a double — needs no decoding at all.

### Optimizer

Constant folding, dead branch elimination, unreachable-statement removal, short
circuit folding and algebraic identities. Every rewrite is one that cannot
change observable behaviour, which rules out two tempting ones:

- **`x * 0` does not fold to `0`.** It is wrong in IEEE arithmetic — `NaN * 0`
  and `inf * 0` are both `NaN` — and it would skip the type error the VM raises
  when `x` is a string.
- **Division by zero is not folded.** It is a runtime error here, so folding it
  would replace an error with a constant and the two paths would disagree.

Deleting a subtree also requires the subtree to be pure. A call might print or
assign, so a call is never pure — being conservative costs an optimisation,
while being wrong deletes the user's side effects.

### Peephole pass

Three superinstructions fold sequences the generator emits constantly:
`INC_LOCAL` for `i = i + 1`, `ADD_LOCAL_CONST`, and `GET_LOCAL_GET_LOCAL`.

Rewriting bytecode after jumps have been emitted is where this usually goes
wrong. Three things make it safe, and skipping any one produces a program that
runs and is subtly incorrect rather than one that crashes:

1. The chunk is decoded instruction by instruction, so a pattern can never
   start in the middle of an operand.
2. An instruction that is the **target of a jump** is never folded into a
   superinstruction — a jump would land inside an operand.
3. Every jump is re-encoded afterwards. The rewrite moves everything after it,
   so the old target offset is mapped through to the new layout rather than
   adjusted in place.

### VM

A stack machine with two dispatch strategies. A `switch` compiles to one
indirect branch shared by every opcode, so the predictor sees a single site with
dozens of targets and mispredicts constantly; threading the dispatch into the
tail of each handler gives every opcode its own site, and opcode sequences are
highly correlated.

Computed goto is the default; `-DLUMEN_COMPUTED_GOTO=OFF` selects the portable
`switch`. Both are built and tested in CI, which is the only thing that keeps
the unused one working. The jump table is padded to 256 entries with every
unused slot pointing at a trap — a `switch` has `default:` and a jump table has
nothing, so an out-of-range opcode should report itself rather than jump into
whatever follows the table.

Opcodes are declared once in an X-macro, and the enum, the disassembler's name
table and the dispatch table are all generated from it. Those three have to
agree exactly — a dispatch table one entry out of step sends every instruction
to the wrong handler — and generating them makes disagreement impossible rather
than merely unlikely.

### Garbage collector

Precise mark-and-sweep. Tracing rather than reference counting for the reason
every language with closures ends up there: a closure capturing a variable that
holds the closure is a cycle, and refcounting leaks it.

The mark phase uses an explicit worklist, not recursion — a long list would
otherwise blow the C++ stack in the middle of a half-marked heap. The intern
table holds weak references; entries whose strings are unreachable are removed
before the sweep, or nothing would ever be freed.

## Results

Apple M2, `./build/lumen_bench`. Each benchmark is best-of-three with a warm-up
run, and is measured with the optimizer on and off:

| benchmark | optimized | baseline | speedup |
| --- | --- | --- | --- |
| loop, 3M iterations | 0.080 s | 0.113 s | **1.40x** |
| nested loops, 2000×1000 | 0.054 s | 0.069 s | **1.29x** |
| list build + sum, 500K | 0.045 s | 0.054 s | 1.21x |
| closure counters, 200K | 0.011 s | 0.013 s | 1.20x |
| string building, 50K | 0.040 s | 0.039 s | 1.00x |
| fib(27) recursive | 0.023 s | 0.024 s | 1.01x |

`fib` shows 1.01x because no rewrite applies to it — and that is the honest
number. An earlier version of this benchmark reported the optimizer making
`fib` **30% slower**, which was entirely an artefact of the first timed
configuration absorbing the process's page faults. Best-of-three with a warm-up
made it go away.

### A 36x win from deleting work, not adding it

`string building` originally took **1.465 s**. Two causes, both from a design
decision that is right for identifiers and wrong for computed strings:

- Every concatenation **interned** its result, hashing the entire accumulated
  string and inserting it into a table that never shrank — once per iteration.
- Every string **hashed eagerly** at construction, a second full pass over
  bytes that were usually never used as a key.

Interning is now applied only to strings at or below 32 bytes, and hashes are
computed lazily on first use. String equality can no longer assume equal strings
are the same pointer, so it falls back to comparing contents — length first,
which is free and rejects most unequal pairs.

**1.465 s → 0.040 s.**

## Tests

92 tests, no framework dependency — `tests/test_framework.hpp` is about 120
lines.

```
./build/lumen_tests           # all
./build/lumen_tests Optimizer # substring filter on suite or test name
make asan                     # the suite under AddressSanitizer and UBSan
```

The ones that carry weight:

- **`Examples.EveryOptimizerConfigurationAgrees`** — every example program is
  run under all four combinations of AST optimization and peephole rewriting,
  and the outputs must be identical. An optimizer is correct exactly when it
  does not change what a program does, so this checks that directly rather than
  checking that some particular rewrite happened.
- **`Differential.OptimizerNeverChangesBehaviour`** — the same comparison over
  18 programs chosen to hit combinations the examples miss, including ones that
  raise runtime errors.
- **`Examples.EachSurvivesGcStress`** and the `GC.*` stress tests — every
  program run again with a collection forced on **every single allocation**.
  This is where collector bugs actually surface: a missing root is harmless
  until a collection lands in the one window where the object is reachable only
  from a C++ local.
- **`Peephole.JumpTargetsSurviveTheRewrite`** — a loop with `break` and
  `continue`, so a jump left pointing at its pre-rewrite offset produces a wrong
  answer rather than a crash.
- **`VM.BreakDoesNotLeakStackSlots`** — 100,000 iterations of a loop broken out
  of, which overflows the stack if leaving a scope by jumping fails to discard
  its locals.
- **`VM.TransitiveCapture`** and **`VM.ClosureOutlivesItsFrame`** — a variable
  captured three functions deep, and a closure read after its creating frame is
  gone.

Each example program carries its expected output in `#=` comments at the top, so
an example cannot drift from what it claims to print.

CI builds on Linux and macOS with GCC and Clang, in Debug and Release, at
`-Werror` with `-Wall -Wextra -Wpedantic -Wshadow`, and runs the whole suite
under AddressSanitizer and UndefinedBehaviorSanitizer.

## Bugs this design caught

**A function was allocated before its root was registered.** In
`Compiler::function`, interning the function's name — one line before the
`TempRoot` — allocates, and that allocation could trigger a collection that
freed the function about to be written to. Under a normal heap the window is
almost never hit. Under GC stress it is hit every time, and it was the single
cause of all four failures the first stress run produced.

**Several optimizer assertions were vacuous.** The disassembler printed
`Divide`, while the tests checked for `DIVIDE`, so every `!contains(code,
"MULTIPLY")` passed for the wrong reason. Giving each opcode an explicit display
name in the X-macro fixed it, and `disassemble()` now returns a marker rather
than an empty string when there is no listing, so an empty result can never
satisfy an absence check.

**Tokens outliving their source.** `Token::text` is a `string_view` into the
source, and a test that scanned a temporary left every view dangling the moment
the statement ended.

**A null pointer from unspecified argument evaluation order.** This one cost
five CI round trips, and the write-up is here because the way it was found
matters more than the fix.

GCC builds segfaulted on the first program the VM ran. Clang was fine
everywhere, including under ASan and UBSan. The obvious suspect was the
computed-goto dispatch, since that is the one place the two compilers were being
asked to do something non-standard — so the jump table was moved out of static
storage, padded to 256 entries with a trap, and the tree was swept with clang
`-Wshadow-all`. None of it helped. Turning computed goto off entirely did not
help either, which finally ruled out the theory the previous three changes had
all been built on.

The actual cause was one line in the optimizer:

```cpp
return simplify_algebraic(static_cast<BinaryExpr*>(folded.get()), std::move(folded));
```

Argument evaluation order is unspecified in C++. Clang evaluates left to right,
so `folded.get()` runs before the move and the node pointer is valid. GCC
evaluates right to left, so `std::move(folded)` empties the `unique_ptr` first
and `folded.get()` returns null. Nothing to do with dispatch, nothing to do with
the VM, and invisible to a sanitiser because it is not a memory error — it is a
perfectly legal null pointer being dereferenced.

Two things fixed it properly. The helper now takes ownership and re-derives the
node inside, so the two-argument form that made the mistake expressible no
longer exists. And the CI job that got the answer — running the GCC build under
`gdb` and printing a backtrace — is still there, because the reason this took
five attempts is that the first four were guesses and the fifth was a
measurement. The stdout flushing added along the way matters for the same
reason: the earlier logs were empty because a segfault discards a block-buffered
buffer, so CI reported a crash with no indication of where.

## Language

Dynamically typed, with numbers (doubles), strings, booleans, `nil`, lists and
first-class functions with closures.

```
let x = 1;                        # declaration; block scoped
fn add(a, b) { return a + b; }    # functions
let f = fn(x) { return x + 1; };  # lambdas
if (c) { ... } else { ... }
while (c) { ... }
for (let i = 0; i < n; i = i + 1) { ... }
break; continue;
let xs = [1, "two", nil];         # lists, mixed types
xs[0]; xs[-1]; xs[0] = 9;         # indexing, negative from the end
"a" + "b"; [1] + [2];             # concatenation
print value;
```

Builtins: `len` `str` `num` `type` `push` `pop` `sqrt` `floor` `abs` `clock`.

Two deliberate choices worth naming:

- **Only `nil` and `false` are falsey.** Zero and the empty string are truthy,
  which removes a class of bug where a valid empty value silently takes the
  wrong branch.
- **Assigning to an undeclared name is an error**, not an implicit declaration.
  Silently creating it is how a misspelling becomes a bug that surfaces
  somewhere else entirely.


## Scope

Not implemented, each a real change rather than a missing detail:

- **Classes and inheritance.** The object model has the header and the tracing
  hooks; methods need a bound-method object and a `this` slot.
- **A generational or incremental collector.** The current one stops the world
  and traces the whole heap, so pause time is proportional to live data.
- **Persistent REPL state.** Each line is its own program; keeping globals would
  mean keeping one VM alive across lines, which changes who owns the heap.
- **A register VM.** The stack machine executes more instructions per unit of
  work; a register design would need an allocator and would change every
  opcode.
